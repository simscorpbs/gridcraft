# AutoSave in synced cloud folders

GridCraft uses the desktop sync clients' ordinary folders. It does not connect to a cloud API. A workbook saved in one of these folders is uploaded by the installed client and becomes available on the person's other devices. Ported from the behaviour of the WordCraft fork (`docs/cloud.md` there), including its version history.

## Folder discovery

On macOS, GridCraft checks `~/Library/Mobile Documents/com~apple~CloudDocs` for iCloud Drive, each `GoogleDrive-<account>` and `OneDrive-<account>` under `~/Library/CloudStorage`, then older `~/Google Drive` and `~/OneDrive` folders. On Windows, iCloud Drive is `%USERPROFILE%\iCloudDrive`; Google Drive may be a drive letter whose root contains `My Drive` (including localized client names) or a mirrored profile folder; OneDrive uses `%OneDriveConsumer%`, `%OneDriveCommercial%` or `%OneDrive%`. On Linux and other systems there is no assumed client path; `GRIDCRAFT_CLOUD_ICLOUD`, `GRIDCRAFT_CLOUD_GDRIVE` and `GRIDCRAFT_CLOUD_ONEDRIVE` can name folders. The browser build has no folders to discover.

The desktop app discovers the roots once, off the UI thread. `file.cloud` reports provider, root, current path, conflict state and the discovered roots. Provider ids are `icloud`, `gdrive` and `onedrive`. iCloud-only files must be downloaded by the sync client before opening.

## Save a new workbook

Turning AutoSave on for a workbook that was never saved opens the Save to Cloud dialog (or Save As when no cloud folder was found). `file.saveToCloud` accepts optional `provider` and `name` (without extension). With no provider, the first discovered root is chosen in iCloud Drive, Google Drive, OneDrive order. The file is written as a new `.xlsx` in that provider's documents folder, using a numbered name when needed.

## Conflict protection

`file.save` with `{"ifUnchanged": true}` (what AutoSave sends) first checks that the workbook's file still holds what GridCraft last read or wrote (size, date and a digest of the bytes). If another device or program changed it, or it was deleted or moved, nothing is written: the result has `conflict` (`changed` or `missing`), the Save Conflict dialog opens and AutoSave stays paused for that workbook. `file.resolveConflict` takes `keep`: `both` (save this version beside the other as `Name (conflict copy).xlsx` and keep editing that), `mine` (overwrite; for a missing file, save it here again) or `theirs` (reopen the file as it is now, discarding unsaved changes here). A plain Save is the person's own decision and still writes.

## Closing and quitting

With AutoSave on, closing a changed workbook (`file.close`, `window.close`, quitting) first writes the pending changes with `ifUnchanged` and goes on without a Save Changes prompt. If another device changed the file, the Save Conflict dialog opens instead and the workbook stays open. If a Save Changes prompt was already visible, a successful AutoSave closes it and the workbook. With AutoSave off for the file, or a write that fails, the Save Changes prompt stays in charge.

## AutoSave for each file

AutoSave is on by default for every workbook whose file exists on disk in a format that keeps everything (`.xlsx`, `.xlsm`, `.xltx`, `.xltm` and GridCraft's own `.json`), local or in a cloud folder, and an opened file is covered at once. The switch is off, with the reason in its tooltip, for a new workbook, a format that loses things (csv, text, web page), a workbook opened from bytes, the browser, and a file with a conflict waiting.

A write that fails (another program holds the file, a full disk) does not turn AutoSave off. It pauses and tries again after 5 seconds, then waits twice as long after each further failure, up to one minute. The status bar shows the error while writes keep failing and the message goes away after the next successful write. Successful writes are at least two seconds apart.

Each file remembers its switch in `<settings_dir>/autosave.json`, never in the workbook. Turning AutoSave off for a file is remembered when it is opened again; turning it back on forgets the choice. Paths are normalised (on Windows the `\?\` prefix is removed, separators become `\` and case is ignored; case is also ignored on macOS). The file keeps at most 2000 entries, drops the oldest first, is read only up to 1 MiB and is written atomically. Save As, Save to Cloud and Keep both give the new file the switch the workbook had.

File › Options › Save › **Turn on AutoSave by default** (`file.options` with `{"autosaveByDefault": bool}`, saved with the preferences as `autosaveByDefault`) sets the default for files with no choice of their own. It is on by default.

`file.autosave` with `{"value": bool}` (or `{}` to toggle) sets the active workbook's switch and remembers it for the file; it fails with the reason when AutoSave cannot cover the workbook. `file.cloud` reports `autosave: {on, default, remembered, covers, blocked}`.

## Version history

The desktop app keeps a local history for each saved workbook. By default it is in `<settings_dir>/versions/`, in one folder per workbook. A workbook package (`.xlsx`, `.xlsm`, `.xltx`, `.xltm`) is filed under its document id; the other format GridCraft saves in full, its own `.json`, is filed under a hash of its canonical path (on Windows the path is lower-cased first, because file names there ignore case). Each version is described by its own file: the manifest of a version kept as parts, or `<id>.meta.json` beside a whole copy `<id>.bin`. The description gives `id`, `savedAt` (UTC), `author`, `size` (the saved workbook's size), `kind`, `windowStart`, `digest` (SHA-256 of the saved bytes), `session`, `capturedAt`, `storage` (`whole` or `parts`), `stored` (the disk space the version added), `supersedes`, `documentId` and `details` (below). Every file the history writes is flushed and read back before it replaces anything, and the history folders are created private to the user (mode 0700 on Unix). History is written in the background. A failure in the history is reported (`Session::versions_error`) and logged. It never stops a save and never changes the bytes saved, apart from the document id (below). Only the workbook's own file has a history: a copy exported in another format, such as CSV, PDF or HTML, does not create one.

Only the desktop app keeps a history. A session the host did not start one for (the command line, MCP, scripts, tests) writes none, and opening a workbook never writes any. A history is written by `file.save`, `file.saveAs`, `file.saveToCloud` and `file.resolveConflict`, the commands that write a workbook's own file, and by AutoSave through `file.save`. The browser build keeps none.

Every explicit save creates a version. Excel's AutoSave on OneDrive adds a version at the first change after a workbook opens and then about every ten minutes. GridCraft does the same: the first AutoSave write of each editing session (one opening of the workbook; GridCraft keeps several workbooks open at once, each with its own session) starts a new version, and later writes from that session update it until ten minutes have passed since the version was started. Closing a changed workbook with AutoSave on writes it with `file.save` and `"trigger": "close"`, so the last write before it closes is always in the history.

Before any save writes over a file whose current bytes are not already in its history, GridCraft stores those bytes byte for byte, synchronously, before the file is replaced. The version is `original` when the workbook had no history yet: a `.xlsx` made before GridCraft was installed, or the file Save As replaces. It is `external` when another program or computer changed a file that already had a history. `savedAt` is the file's modification time. The file is read once for each opened workbook, and later saves only compare the disk stamp.

A `.xlsx` is a zip archive whose parts are compressed separately, so a one-cell edit changes most of the file's bytes and a byte diff of two saves is almost as large as the file. The history therefore opens the archive and keeps each part as an object in `objects/`, named by the SHA-256 of its content, as git names its blobs. A picture, theme or style part that did not change between saves is stored once. A part that changed is stored as a delta against the same part of the previous version: the shared start and end are copied, and the rest is matched in 32-byte blocks with a rolling hash. The delta is then compressed. After ten deltas in a row, or when a delta would be more than half the size of the compressed part, the part is stored whole again. A restore therefore reads at most eleven objects for a part, and one damaged object affects only the versions whose chain passes through it.

Each version kept this way is a manifest, `<id>.parts.json`, that lists the parts in archive order with their names, compression method, dates, sizes and hashes, and repeats the version's metadata. Opening or restoring a version rebuilds the archive from the manifest. Every part is checked against its hash. The rebuilt zip can differ from the saved file in its compressed bytes, but each part has the same content. Before a version is stored as parts, the archive is rebuilt in memory and split again to confirm that it comes back with the same parts. The `original` version, the bytes that were on disk before GridCraft wrote over them, is always kept byte for byte as `<id>.bin`. So is any file that is not a zip or that exceeds the limits: more than 10,000 parts, one part over 256 MiB, or more than 1 GiB in total uncompressed. Those limits are checked against the sizes the archive declares, and every read is capped at the declared size, so a zip bomb is stored whole and never inflated. If anything in the parts path fails, the version is stored whole instead.

An object that already exists is reused only if it still reads back correctly. A damaged object is written again whole, which also repairs every version that uses it. Versions stored whole move to parts gradually, one per save, newest first, after their parts are confirmed to read back.

Retention follows the automatic version limits of SharePoint and OneDrive for work. All versions are kept for 30 days. From 30 to 60 days, the newest version of each hour is kept. From 60 to 180 days, the newest of each day is kept. After that, the newest of each week is kept. Age alone never empties a history. Each workbook keeps at most 500 versions and 500 MiB of real disk space, newest first, with a part shared by several versions counted once. Objects that no kept version needs, either directly or as the base of a delta, are deleted after pruning. If any manifest or object header cannot be read, nothing is deleted on that pass. The oldest `original` version is pinned: it outlives the time rules and is the last version to go under the count and size limits. A personal OneDrive keeps only the last 25 versions; the local history keeps more because it is private to the computer. A damaged `index.json` (the one file some earlier tools wrote) is read one entry at a time, and version files that the index does not mention are listed again from their own files, so pruning never deletes them only because the index lost them. A version whose bytes no longer match its digest is refused.

Each workbook package gets a random document id, a UUID version 4 that is derived from nothing: not the computer, the user, the time or the path. It is stored in `docProps/custom.xml` as the custom property `GridCraftDocumentId` (ECMA-376 Part 1 §22.3), added to the finished package by `gridcraft_xlsx::set_custom_property`, which copies every other part as it is. Excel keeps custom properties when it saves, so the id survives a round trip through Excel. The id is assigned at the workbook's first save, whether it was created in GridCraft or received from someone else, and nothing else about the history is written into the file. The history follows the id, so a file renamed or moved, inside or outside the app, keeps its history, as OneDrive keeps a file's history through a rename or move (`file.rename` renames the file on disk and tells the history through `Session::versions_renamed`; a host that renames a file some other way calls it itself). On the first save under an id, the history the file had by path moves under the id.

Save As, Save to Cloud and Keep both write a new file. It gets a new id, and its first version, of kind `saveAs` or `conflictCopy`, records the workbook and version it came from in `details.origin`. The original file keeps its own history. This is the same as copying a file in OneDrive, where only the latest version comes along. A copy made outside the app, such as two files carrying the same id while the one the history last saw still exists, gets a new id at its next save and records its origin the same way (`trigger` is `copy`). A file that only moved keeps its id. When the workbook has "remove personal information on save" turned on (`removePersonalInfo`), no id is written into the file (one it carried is taken out) and its history is kept by path. Files kept by path are found again after a move outside the app: a folder matches when its recorded path no longer exists and its newest version holds exactly the bytes now in the file.

The history can be kept in one or two folders (File › Options › Save › Version History, `file.options` `versionsFolder`, `versionsMirror`). The default is the settings folder alone. Another folder can replace it, or both can be used as mirrors. Every write goes to every folder that can be reached, and listing and reading use all of them. A folder that cannot be reached, because a drive is unplugged or permission was removed, does not stop the save. It is reported by `Session::version_folders` and by `file.options` as `versionsUnavailable`, and brought up to date when it is back: each folder receives the version files and objects another one has and it lacks. When the folders change, the history already kept is copied, moved or left in place (`versionsExisting`: `copy`, the default, `move` or `leave`). `versionsFolder` is an existing folder given as a full path (or one starting with `~/`), or `default` for the settings folder alone. The device name versions record (`deviceLabel`, or `auto` for the system's) is set the same way. The settings are saved with the preferences as `versionsFolder`, `versionsMirror` and `deviceLabel`.

A history folder can be one that a cloud app syncs between two computers, because nothing in it is ever rewritten. Each version is an immutable file with a random name, and objects are named by their content. AutoSave joining the version of its window writes a new version that `supersedes` the old one instead of rewriting it. There is no shared index: the list is rebuilt from the versions' own files and cached in memory. Retention decisions depend only on the versions' records, so two computers make the same decisions. An object that no kept version needs is deleted only after it has stayed unneeded for 7 days: a dated mark is left in `gc/` the first time, and the mark is removed if a version needs the object again. One computer therefore never deletes an object the other has just written before its manifest arrives. Files that are not the history's own, partly synced files, and a sync app's conflict copies (`name (1).parts.json`, `name-DESKTOP-1.meta.json`) are ignored and never deleted. A history folder inside iCloud Drive, OneDrive or Google Drive is as private as that account: anyone with access to it can open the earlier versions.

`file.versions` with `{}` lists versions newest first and returns `{index,id,savedAt,author,size,stored,kind}`, where `stored` is the disk space the version added, and also `storage`, `documentId`, `supersedes` and `details`. `{"delete":"document"}` deletes the active workbook's history and `{"delete":"all"}` deletes every workbook's history, in every history folder; File › Options › Save › Version History has buttons for both, each with a confirmation. The list is read when the call is made, so the first call after a workbook opens already returns its versions. `{"open":"id"}` returns the version's metadata and its bytes (`base64`, a `.xlsx`; `tooLarge` instead above 32 MiB) and opens nothing (`file.openVersion`, below, opens it). `{"restore":"id"}` replaces the active workbook's content with that version in one Undo step. Unsaved changes are first stored as an `autosave` version (trigger `beforeRestore`), so the state before the restore stays in the history. The restored bytes are then recorded at once as a new `restore` version, whether or not AutoSave writes the file afterwards. Sheet protection applies to a restore as to any other edit.

File › Info › Version History opens the right-hand history pane. Clicking the workbook name in the title bar (left or right button) opens a small file menu, as Excel does for a OneDrive workbook: the file name, which can be changed there and applied with Enter (`file.rename`); the folder that holds the file, or Not saved; and Version History. `file.rename` with `{"name": "Budget"}` renames the active workbook's file in its folder and adds the extension when the name lacks it. It refuses a file that already exists, a name with a folder or with characters Windows does not allow, and a workbook with no file. The file keeps its version history, its AutoSave switch, its disk stamp and its place in Recent. The pane lists versions newest first under day headings: Today, Yesterday, or the date (month names in English and Brazilian Portuguese, an ISO date in other interface languages). Each row shows the local time and the author, with an Open version link; hovering a row shows its full date and time, and right-clicking it offers Open version and Restore. With no versions the pane says why: the workbook has not been saved yet, the history is empty, or (in the browser) the history is kept by the desktop app. A shown previous version keeps the pane on the history of the workbook it came from.

GridCraft keeps several workbooks open, so a previous version is one more workbook, shown beside the current one and not in its place. `file.openVersion` with `{"id": "..."}` opens that version of the active workbook's history as a read-only workbook named `Name (version <local date time>).xlsx`; the title bar reads `Name (version <local date time>) — Previous version`. Before it opens, AutoSave writes the current workbook if it has unsaved changes, so that state is in the history too (a save conflict found by that write opens the Save Conflict dialog and nothing opens). A version already open is brought forward. The version has no file and no AutoSave. Commands that would change it, including Undo and Redo, Save and Save As, are refused with a status message (`This is a previous version. Restore it or save a copy to make changes.`); ribbon commands that change a workbook are greyed out with that reason, and typing into a cell does not start. The view, moving the selection, selecting, copying, exporting and the file commands that do not write this workbook work as before. Its row in the pane is highlighted and has no link. A Previous version bar above the sheet shows the date, time and author with **Compare**, **Restore**, **Save a copy** and **Close**.

- **Compare** (`file.compareVersion`, `{"on": true|false}`, default a toggle) shows the previous version with every cell that differs from the current workbook highlighted: a cell whose value or formula changed, and a cell the current workbook has and the version lacks. Sheets are matched by name; a sheet only one of them has is named in the result (`onlyInVersion`, `onlyInCurrent`) and not highlighted. At most 100,000 cells are highlighted (`truncated`). The comparison takes the version's place and stays read only; pressing Compare again shows the version.
- **Restore** (`file.restoreVersion`) goes back to the current workbook and runs `file.versions` with `{"restore": id}`: the version becomes the workbook's content in one Undo step and is recorded at once as a `restore` version. The version closes. Restoring another version from the pane's menu while one is shown closes the one shown first.
- **Save a copy** (`file.saveVersionCopy`, `{"path": ...}`; the interface asks where) saves the version as a new file and then goes back to the current workbook. The copy gets a new document id and its first version, of kind `saveAs`, records the workbook and the version it came from in `details.origin`. A comparison is never saved: the copy holds the version as it was saved. The workbook the version came from is never overwritten.
- **Close** (`file.closeVersion`) closes the version and activates the workbook it came from, which was never touched: its unsaved changes, undo history, selection and AutoSave stamp are as they were. File › Close on a version does the same, and stops there.

New and Open while a version is shown first close it, so they start from the current workbook; the new or opened workbook then appears beside it as usual. Quitting does the same before it asks about unsaved changes, so a shown version never hides a workbook's unsaved work. If the workbook a version came from is closed meanwhile, the version stays open and can be saved as a copy or closed, but not compared or restored.

Each version's `details` records, as far as is useful and no further:

- the previous version (`parent`), the origin of a copy, and which parts of the package changed or were removed;
- the UTC time with the local offset, the start of the editing session and how long it had run, and the AutoSave window;
- the kind and what caused the save (`trigger`): `save`, `autosave`, `close` (`file.save` with `"trigger":"close"`), `restore:<version>`, `saveAs`, `conflictCopy`, `copy`, `beforeSave` or `beforeRestore`;
- the author's name and initials (from the user name in the preferences), unless the workbook removes personal information;
- a random installation id, made once and kept in the settings folder, and a device label the user can edit in Options (by default only the system name, "Windows" or "Mac"), with the operating system and its version and the GridCraft version and commit. The host name and account name are never recorded;
- the path relative to the provider's folder or the user's folder (`onedrive:/Reports/x.xlsx`, `~/Documents/x.xlsx`), with any folder named after the account replaced by `<user>`, and the provider (`local`, `icloud`, `onedrive`, `gdrive`);
- the size, modification time and SHA-256 of what was on disk before the save;
- the title and creator from the workbook's properties, without the creator when personal information is removed;
- counts of sheets, used cells, formulas, charts and comments.

No content of the workbook goes into the records; only counts and hashes do. No location, IP address or keystrokes are recorded.

## Limits

The feature depends on a compatible sync client being installed and signed in. There is no cloud API, server-side merge or real-time co-authoring. The version history described above is kept in the desktop profile, or in the folders chosen in Options, is not synchronized by GridCraft itself (a folder a sync app keeps is), and is unavailable in the browser. iCloud Drive, Google Drive and OneDrive keep their own server-side histories; GridCraft does not browse or merge those histories. Renaming files is not a GridCraft command, so the remembered AutoSave choice does not need to follow a rename.
